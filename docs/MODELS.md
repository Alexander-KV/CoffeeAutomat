# Модель предметной области: `CoffeeMachineApp2/Models`

[Оглавление руководства](DEFENSE.md) · [Короткая шпаргалка](QUICK_DEFENSE.md)

Исходники: [Beverage.cs](../CoffeeMachineApp2/Models/Beverage.cs), [CoffeeOrder.cs](../CoffeeMachineApp2/Models/CoffeeOrder.cs), [MachineConfiguration.cs](../CoffeeMachineApp2/Models/MachineConfiguration.cs), [CoffeeMachine.cs](../CoffeeMachineApp2/Models/CoffeeMachine.cs), [Payment.cs](../CoffeeMachineApp2/Models/Payment.cs).

В пяти файлах находятся восемь типов: три записи с данными (`record`), три класса с поведением, один интерфейс и одно перечисление. Пространство имён — `CoffeeMachineApp.Models`. Модель рассчитывает цену, проверяет данные, проводит оплату и управляет этапами заказа. Она не рисует интерфейс и сама не записывает JSON.

| Файл / тип | Назначение и причина отдельного типа |
|---|---|
| `Beverage.cs` → `sealed record Beverage` | Описание одного напитка: название, цена, рецепт, оформление, доступность. Эспрессо и латте являются разными данными одного типа; отдельные подклассы для них не нужны. |
| `CoffeeOrder.cs` → `sealed record CoffeeOrder` | Выбранный напиток с добавками и вычисляемой итоговой ценой. Меню хранит базовый напиток, заказ — выбор конкретного покупателя. |
| `MachineConfiguration.cs` → `sealed record MachineConfiguration` | Сохраняемые настройки одного автомата: идентификатор, название, меню. Умеет проверять и копировать настройки. |
| `CoffeeMachine.cs` → `enum MachineState` | Четыре этапа заказа: выбор, оплата, приготовление, выдача. Убирает необходимость определять этап по случайному сочетанию флагов. |
| `CoffeeMachine.cs` → `sealed class CoffeeMachine` | Один работающий автомат: собственные настройки, заказ, наличные, карта, сдача и состояние. Координирует допустимые действия. |
| `Payment.cs` → `interface IPaymentMethod` | Общий контракт оплаты: название способа и операция `Pay(total)`, возвращающая сдачу. |
| `Payment.cs` → `sealed class CashPayment` | Приём разрешённых купюр, накопление внесённой суммы, оплата, возврат и разложение сдачи по номиналам. |
| `Payment.cs` → `sealed class CardPayment` | Учебная карта с неограниченными средствами; оплата доступна только после вставления карты. |

`sealed` запрещает наследование от этих классов и записей. Расширение ассортимента предусмотрено через данные `Beverage`, а не через наследование от `Espresso`, `Latte` и других классов.

## `Beverage`: свойства и правила проверки

Все свойства имеют `get; init;`: их можно задать при создании объекта или получить изменённую копию через `with`. Конструктор не запускает `Validate()` автоматически.

| Свойство | Значение по умолчанию | Что реально проверяется / как используется |
|---|---|---|
| `string Id` | Новый `Guid`, строка формата `N` | `Guid.TryParseExact(Id, "N", ...)`: 32 шестнадцатеричных символа без дефисов. Этот метод не проверяет уникальность среди других напитков. |
| `string Name` | `"Новый кофе"` | Не `null`, не пустое и не из одних пробелов; длина не больше 60. Пробелы по краям автоматически не удаляются. |
| `decimal Price` | `150` | От 1 до 9999 ₽ включительно; доли копейки не допускаются (`decimal.Round(Price, 2) == Price`). |
| `int VolumeMl` | `200` | От 30 до 1000 мл включительно. |
| `string Recipe` | `"Эспрессо и горячая вода"` | Непустой текст до 200 символов. Это описание, а не выполняемая программа приготовления. |
| `string ImageFile` | `"coffee1.png"` | Не `null`, не длиннее 100 символов, без `/` и `\`, равен результату `Path.GetFileName`. Пустая строка разрешена. Наличие файла и его расширение здесь не проверяются. |
| `string LiquidColor` | `"#70462D"` | Проверяется выражением `^#[0-9a-fA-F]{6}$`, рассчитанным на `#RRGGBB`; регистр не важен. |
| `bool HasMilk` | `false` | Признак молока в базовом напитке; отдельной проверки нет. |
| `bool IsCoffee` | `true` | Признак кофейного напитка; отдельной проверки нет. |
| `bool IsEnabled` | `true` | Доступен ли выбор напитка покупателю. Проверяется при `CoffeeMachine.Select()`, а не как условие валидности записи. |
| `int PrepareSeconds` | `6` | От 2 до 60 секунд включительно. Сам объект `Beverage` не запускает таймер. |

| Объявленный метод | Вход → результат | Действие | Ошибки | Зачем нужен |
|---|---|---|---|---|
| `public void Validate()` | Текущий объект → `void` | Последовательно проверяет ID/название, цену, объём/время, рецепт, цвет и имя картинки. | `ArgumentException` при первой нарушенной проверке. | Одна проверка данных для меню, заказов, сохранения и загрузки. |

## `CoffeeOrder`: заказ и цена

Позиционная запись объявляет свойства `Beverage`, `Sugar`, `ExtraMilk`, `Syrup` с `get; init;`. Параметры по умолчанию: сахар `0`, дополнительное молоко `false`, сироп `"Без сиропа"`.

`Total` — вычисляемое свойство типа `decimal`:

```text
цена напитка
+ 10 ₽, если Sugar > 2
+ 30 ₽, если ExtraMilk == true
+ 30 ₽, если Syrup != "Без сиропа"
```

Сахар в количестве 0–2 бесплатный; 3 и 4 ложки дают одинаковую доплату 10 ₽ за заказ. Дополнительное молоко оплачивается независимо от `Beverage.HasMilk`. Сиропы «Ваниль» и «Карамель» имеют одинаковую доплату. Ограничение 9999 ₽ относится к базовой цене напитка: корректный заказ с добавками может стоить до 10069 ₽.

| Объявленный метод / конструктор | Вход → результат | Действие | Ошибки | Зачем нужен |
|---|---|---|---|---|
| `CoffeeOrder(Beverage Beverage, int Sugar = 0, bool ExtraMilk = false, string Syrup = "Без сиропа")` | Напиток и параметры → новый заказ | Первичный конструктор позиционной записи присваивает свойства. | Собственных проверок нет; можно создать некорректный объект, включая `Beverage = null`. | Объединяет выбор покупателя в один объект. |
| `public void Validate()` | Текущий заказ → `void` | Проверяет наличие напитка, вызывает `Beverage.Validate()`, проверяет сахар 0–4 и сироп из трёх допустимых строк. | `ArgumentException` при отсутствии/некорректности напитка, неверном сахаре или сиропе. | Не позволяет принять неподдерживаемые настройки заказа. |

`Total` сам не вызывает `Validate()`: при `Beverage = null` чтение цены вызовет `NullReferenceException`, а неизвестный сироп до проверки даст доплату 30 ₽. В нормальном сценарии автомат проверяет заказ перед оплатой.

## `MachineConfiguration`: меню, снимок и копия автомата

| Свойство | Значение по умолчанию | Правило |
|---|---|---|
| `string Id` | Новый GUID в формате `N` | Корректный GUID формата `N`; при обновлении существующего автомата менять его запрещено. |
| `string Name` | `"Кофейня №1"` | Непустое название до 40 символов. |
| `IReadOnlyList<Beverage> Menu` | `Array.Empty<Beverage>()` | Для валидной конфигурации требуется 1–100 ненулевых напитков; каждый проходит проверку; строковые ID внутри меню не повторяются. |

Пустое меню по умолчанию означает, что `new MachineConfiguration()` без заполнения `Menu` ещё не является валидной настройкой. Меню, где все напитки выключены, валидно, но купить в нём нечего.

| Объявленный метод | Вход → результат | Действие | Ошибки | Зачем нужен |
|---|---|---|---|---|
| `public void Validate()` | Настройка → `void` | Проверяет ID/название, размер и элементы меню, вызывает проверку каждого напитка, сравнивает количество разных ID с количеством напитков. | `ArgumentException` при первой ошибке, включая повтор ID в одном меню. | Проверяет настройку как единое целое. |
| `public MachineConfiguration Snapshot()` | Текущая настройка → новая запись | `this with { Menu = Array.AsReadOnly(Menu.ToArray()) }`: копирует контейнер меню и оборачивает массив в коллекцию только для чтения. ID автомата и напитков сохраняются; сами записи напитков не копируются. | Собственной валидации нет; при `Menu = null` LINQ выбросит `ArgumentNullException`. | Защищает рабочий автомат от последующей замены элементов исходного списка. |
| `public MachineConfiguration Duplicate(string name)` | Название копии → новая настройка | Создаёт новый ID автомата, меняет название, для каждого напитка создаёт `with`-копию с новым ID; создаёт отдельный массив и оболочку только для чтения. Остальные поля напитков сохраняются. | Собственной валидации нет: некорректное название вернётся в результате; при `Menu = null` — ошибка LINQ, при `null`-элементе — ошибка обращения к записи. | Подготавливает самостоятельный автомат с таким же ассортиментом и новыми идентификаторами. |
| `public static MachineConfiguration CreateDefault()` | Нет → готовая настройка | Создаёт меню из девяти напитков через `Drink(...)`; у горячего шоколада дополнительно устанавливает `IsCoffee = false`. ID формируются при создании объектов. | Явных проверок/исключений нет; использованы фиксированные корректные значения. | Даёт начальный ассортимент при первом запуске. |
| `private static Beverage Drink(string name, decimal price, int volume, string recipe, int image, bool milk, string color)` | Данные рецепта → `Beverage` | Заполняет название, цену, объём, рецепт, картинку `coffee{image}.png`, молочный признак и цвет; остальные свойства получают обычные значения по умолчанию. | Сам не проверяет входные данные. | Убирает повторяющиеся инициализаторы в стартовом меню. |

Стартовое меню: эспрессо 120 ₽/60 мл; американо 140 ₽/200 мл; капучино 180 ₽/300 мл; латте 190 ₽/300 мл; латте макиато 200 ₽/300 мл; моккачино 210 ₽/300 мл; флэт уайт 200 ₽/250 мл; раф 220 ₽/300 мл; горячий шоколад 180 ₽/250 мл. Все включены и получают `PrepareSeconds = 6`. У первых двух `HasMilk = false`, у остальных `true`; только горячий шоколад имеет `IsCoffee = false`.

**Точная разница между `Snapshot()` и `Duplicate()`:**

| Что сравниваем с оригиналом | `Snapshot()` | `Duplicate("Кофейня №2")` |
|---|---|---|
| Объект конфигурации | Новый | Новый |
| ID автомата | Тот же | Новый GUID |
| Название | То же | Переданное название |
| Контейнер меню | Новый, с оболочкой только для чтения | Новый, с оболочкой только для чтения |
| Объекты напитков | Те же ссылки | Новые записи |
| ID напитков | Те же | Новый GUID у каждого |
| Текущий заказ, карта, наличные | Не входят в конфигурацию | Не копируются; появятся заново при `new CoffeeMachine(copy)` |

Пример: было `MachineId = A`, напитки `B` и `C`. После `Snapshot()` остаются `A/B/C`; после `Duplicate()` получаются новые `D/E/F`. Новая конфигурация сама по себе ещё не является работающим автоматом: для неё создаётся отдельный `CoffeeMachine`.

Проверка GUID подтверждает формат, а не глобальную уникальность. `Validate()` меню ищет повторы через обычное строковое `Distinct()`; регистр строк учитывается, поэтому два по-разному записанных регистра одного GUID не будут сочтены одинаковыми ID. ID, которые генерирует сам проект, имеют единый формат `Guid.NewGuid().ToString("N")`. Совпадение ID разных автоматов модель `MachineConfiguration` сама не проверяет.

## Оплата: `IPaymentMethod`, `CashPayment`, `CardPayment`

| Тип / свойство | Значение и смысл |
|---|---|
| `IPaymentMethod.Name` | Доступное только для чтения название способа оплаты. В интерфейсе реализации нет. |
| `CashPayment.Name` | Всегда `"Наличные"`. |
| `CashPayment.Inserted` | `decimal`, начальное значение 0; накопленные деньги до успешной оплаты/возврата. Установить свойство снаружи нельзя. |
| `CardPayment.Name` | Всегда `"Банковская карта"`. |
| `CardPayment.IsInserted` | `bool`, сначала `false`; меняется через `Insert()`/`Eject()`. |

| Объявленный метод | Вход → результат | Действие | Ошибки | Зачем нужен |
|---|---|---|---|---|
| `IPaymentMethod.Pay(decimal total)` | Сумма → `decimal` сдачи | Объявляет контракт; тело отсутствует. Поведение определяет выбранная реализация. | Определяются реализацией. | Позволяет автомату вызывать оплату одинаковым способом для карты и наличных. |
| `CashPayment.Insert(int amount)` | Целый номинал → `void` | Принимает только 10, 50, 100 и 500 ₽; прибавляет сумму к `Inserted`. | `ArgumentException` для любого другого числа. | Моделирует купюроприёмник. |
| `CashPayment.Pay(decimal total)` | Цена → сдача | Проверяет положительную цену и достаточность денег; вычисляет `Inserted - total`, обнуляет `Inserted`, возвращает сдачу. | `ArgumentOutOfRangeException`, если `total <= 0`; `InvalidOperationException`, если денег мало. При этих ошибках деньги остаются на балансе. | Завершает оплату наличными одним действием. |
| `CashPayment.Refund()` | Нет → возвращаемая сумма | Запоминает `Inserted`, обнуляет его, возвращает прежнюю сумму. Повторный вызов возвращает 0. | Явных ошибок нет. | Возвращает деньги при отмене, возврате к выбору или переходе на карту. |
| `CashPayment.SplitChange(decimal amount)` | Сумма → `IReadOnlyList<decimal>` | Жадно разбивает сумму по убывающим номиналам: 500, 100, 50, 10, 5, 2, 1, 0,50, 0,10, 0,05, 0,01 ₽. Возвращает `AsReadOnly()`; для нуля — пустой список. | `ArgumentException`, если сумма отрицательная либо содержит доли копейки. | Даёт точные номиналы для отображения выдаваемой сдачи, в том числе копеек. |
| `CardPayment.Insert()` | Нет → `void` | Устанавливает `IsInserted = true`. | `InvalidOperationException`, если карта уже вставлена. | Запрещает повторное вставление одной карты. |
| `CardPayment.Eject()` | Нет → `void` | Устанавливает `IsInserted = false`. | `InvalidOperationException`, если карты нет. | Моделирует возврат карты и запрещает повторное изъятие. |
| `CardPayment.Pay(decimal total)` | Цена → `0m` | Проверяет положительную цену и наличие карты; всегда успешно оплачивает корректную сумму без сдачи. Карту не извлекает. | `ArgumentOutOfRangeException`, если `total <= 0`; `InvalidOperationException`, если карта не вставлена. | Реализует учебную безлимитную карту без пополнений и остатка 2000 ₽. |

`decimal` подходит для денежных расчётов с десятичными долями: суммы в копейках здесь не проходят через двоичную погрешность `float`/`double`. Методы `Pay` сами не ограничивают цену двумя знаками после запятой; в обычном заказе это обеспечивается проверкой `Beverage.Price` и целыми доплатами.

## `CoffeeMachine`: свойства и инварианты

| Свойство | Начальное значение | Роль |
|---|---|---|
| `Configuration` | Проверенный снимок переданной конфигурации | Рабочие настройки данного автомата; заменить через setter снаружи нельзя. |
| `State` | `Choosing` | Этап заказа; меняется методами автомата. |
| `Order` | `null` | Выбранный заказ или отсутствие заказа. |
| `Cash` | Новый `CashPayment` | Собственный приёмник наличных; свойство без setter, но объект изменяемый. |
| `Card` | Новый `CardPayment` | Собственная карта/терминал этого автомата; свойство без setter, но объект изменяемый. |
| `UseCard` | `false` | Выбранный способ оплаты: `false` — наличные, `true` — карта. |
| `Change` | `0` | Оплаченная, но ещё не забранная сдача. Не то же самое, что `Cash.Inserted`. |
| `DrinkCollected` | `false` | Получена ли приготовленная чашка. После завершения заказа снова сбрасывается. |

При использовании публичных операций самого автомата соблюдаются следующие правила:

- Переход в оплату требует выбранного и проверенного заказа. При недостатке денег состояние остаётся `Paying`, внесённые деньги сохраняются.
- После успешной оплаты состояние — `Brewing`; повторная оплата и отмена оплаченного заказа недоступны.
- Напиток можно получить только в `Ready`. Сдачу можно получить уже в `Brewing` и затем в `Ready`.
- Возврат к выбору, отмена и переключение на наличные требуют предварительно забрать вставленную карту.
- Оплата картой не извлекает карту автоматически. В `Brewing` и `Ready` её можно забрать.
- Заказ полностью завершается только при одновременном выполнении четырёх условий: `State == Ready`, `DrinkCollected`, `Change == 0`, `!Card.IsInserted`.
- Новый напиток нельзя выбрать, пока предыдущий заказ ожидает выдачи чашки, сдачи или карты.
- Обновление конфигурации разрешено только в `Choosing` при `Order == null`, и ID автомата должен остаться прежним.

В таблице `InvalidOperationException` означает недопустимое действие на текущем этапе, `ArgumentException` — некорректные данные. `Require(...)` проверяет только состояние, а не все свойства объекта.

| Объявленный метод / конструктор | Вход → результат | Действие | Ошибки | Зачем нужен |
|---|---|---|---|---|
| `public CoffeeMachine(MachineConfiguration configuration)` | Конфигурация → автомат | Вызывает `Validate()`, затем сохраняет `Snapshot()`; собственные `Cash` и `Card` создаются инициализаторами свойств. | Ошибки валидации; при `configuration = null` — `NullReferenceException`, отдельной проверки на `null` нет. | Создаёт независимый автомат с проверенными настройками. |
| `public void UpdateConfiguration(MachineConfiguration configuration)` | Новые настройки → `void` | Требует `Choosing` и отсутствия заказа; проверяет новую конфигурацию и неизменность ID; сохраняет снимок. | `InvalidOperationException` при занятом автомате; `ArgumentException` при плохих настройках или другом ID; `null` не обработан отдельно. | Применяет отредактированное меню/название без подмены личности автомата. |
| `public void Select(string beverageId)` | ID напитка → `void` | В `Choosing` ищет включённый напиток и создаёт новый заказ со стандартными добавками. Повторный выбор в том же состоянии заменяет заказ. | `InvalidOperationException` при другом этапе либо отсутствующем/выключенном напитке. | Выбирает доступный товар из собственного меню. |

## Конструкторы и методы, которые добавляет компилятор

`Beverage` и `MachineConfiguration` не имеют написанного вручную конструктора: доступен неявный конструктор без параметров, выполняющий инициализаторы свойств. У `CashPayment` и `CardPayment` также неявные конструкторы без параметров; числовые/логические поля первоначально равны 0/`false`. Эти конструкторы не запускают валидацию. У интерфейса и перечисления экземплярных конструкторов нет.

Для `record` компилятор добавляет сравнение значений (`Equals`, `GetHashCode`, `==`, `!=`), строковое представление и инфраструктуру копирования. У позиционного `CoffeeOrder` также создаётся `Deconstruct`. Это сгенерированные возможности C#, а не отдельные написанные автором методы. Конструктор `CoffeeMachine` задан явно, поэтому автомат без конфигурации создать нельзя.

## Сценарий заказа и диаграмма состояний

Пример покупки наличными при стартовом меню:

1. Создаётся `CoffeeMachine(MachineConfiguration.CreateDefault())`: `Choosing`, заказа нет, наличных и сдачи 0, карта не вставлена.
2. `Select(idКапучино)` создаёт заказ на 180 ₽. `Configure(3, true, "Ваниль")` даёт `180 + 10 + 30 + 30 = 250 ₽`.
3. `BeginPayment()` переводит в `Paying`. `InsertMoney(500)` даёт `Cash.Inserted = 500`.
4. `Pay()` возвращает из наличного способа 250 ₽ сдачи: `Cash.Inserted = 0`, `Change = 250`, `State = Brewing`.
5. Сдачу можно забрать сразу: `CollectChange()` вернёт 250 и обнулит `Change`; состояние останется `Brewing`. Повторная выдача невозможна. `SplitChange(250)` даст `[100, 100, 50]`.
6. Внешний код завершает приготовление вызовом `FinishPreparing()`: `Ready`. Затем `CollectDrink()` получает чашку. Поскольку сдача уже получена и карты нет, автомат сбрасывается в `Choosing` без заказа.

Если сначала получить чашку, автомат останется в `Ready` с `DrinkCollected = true`, пока покупатель не получит сдачу. Если оплата была ровной, `Change = 0`, и отдельное получение сдачи не требуется.

Для карты после `BeginPayment()` вызываются `SelectPayment(true)` и `InsertCard()`. `Pay()` создаёт нулевую сдачу и переводит в `Brewing`, оставляя карту вставленной. Карту можно забрать ещё во время приготовления. Если сначала получить готовую чашку, заказ останется `Ready`, пока `EjectCard()` не вернёт карту. Баланс карты не уменьшается: свойства баланса вообще нет.

```mermaid
stateDiagram-v2
    [*] --> Choosing
    Choosing --> Choosing: Select / Configure
    Choosing --> Choosing: Cancel / UpdateConfiguration
    Choosing --> Paying: BeginPayment
    Paying --> Paying: SelectPayment / InsertMoney / InsertCard / EjectCard
    Paying --> Choosing: BackToSelection или Cancel; карта вынута
    Paying --> Brewing: Pay успешно
    Brewing --> Brewing: CollectChange / EjectCard
    Brewing --> Ready: FinishPreparing
    Ready --> Ready: Выдать чашку, сдачу или карту; осталось что-то получить
    Ready --> Choosing: Чашка получена, сдача = 0, карта вынута
```

В диаграмме петли показывают сохранение этапа, а не доступность каждого действия без условий: например, `UpdateConfiguration` дополнительно требует отсутствия заказа, `CollectChange` — положительной сдачи, `EjectCard` — вставленной карты. При `BackToSelection()` заказ сохраняется; при `Cancel()` очищается. Ошибка перехода выражается исключением и сама по себе не переводит автомат на следующий этап.

## Как объяснить ООП и решения на защите

**Инкапсуляция.** Состояние и заказ имеют `private set`; интерфейс вызывает операции `Select`, `Pay`, `CollectDrink`, а не присваивает этап произвольно. Проверки сосредоточены в модели, поэтому не зависят только от того, выключена ли кнопка. Защита не абсолютная: публичные объекты `Cash` и `Card` позволяют напрямую вызывать их методы, минуя проверки `CoffeeMachine`.

**Абстракция и полиморфизм через интерфейс.** `CoffeeMachine.Pay()` выбирает реализацию в переменную `IPaymentMethod` и вызывает один и тот же `Pay(total)`. Наличные проверяют накопленную сумму и возвращают разницу; карта проверяет вставление и возвращает 0. Новый способ должен реализовать контракт, но текущий автомат всё равно придётся изменить: выбор сейчас жёстко задан булевым `UseCard`, а реализации создаются внутри объекта. Полной подключаемости способов оплаты здесь нет.

**Композиция.** Автомат содержит конфигурацию, заказ и собственные объекты оплаты; заказ содержит напиток; меню содержит записи напитков. Для повторного автомата создаётся новый `CoffeeMachine` из `Duplicate()` настроек. Изменяемые состояния заказов, внесённых денег и карт не являются статическими и не разделяются между экземплярами. Наследование от отдельных видов кофе не требуется.

**`record` и `with`.** Записи удобны для данных, у которых нужны копирование и сравнение значений. `Order with { Sugar = 3 }` создаёт новую запись, сохраняя остальные поля; прежняя запись не меняется. Это позволяет сначала проверить новую версию и только потом присвоить её. `with` выполняет поверхностное копирование: ссылочные поля по умолчанию остаются теми же. Именно поэтому `Snapshot()` отдельно копирует контейнер меню, а `Duplicate()` отдельно копирует каждый напиток.

**Границы неизменяемости.** `init` не заменяет проверку данных и не делает все вложенные объекты автоматически неизменяемыми. `IReadOnlyList<T>` запрещает изменение через этот интерфейс, но исходным объектом может быть обычный массив или `List<T>`; `CreateDefault()` как раз помещает в `Menu` массив. `Snapshot()` копирует этот контейнер и закрывает прямое изменение через возвращённую оболочку. Напитки остаются общими ссылками, что приемлемо для текущего `Beverage` с `init`-свойствами и строковыми/числовыми данными. Если в напиток добавится изменяемая коллекция, эту стратегию потребуется пересмотреть.

**Сравнение записей.** «`record` сравнивает по значениям» не означает автоматическое глубокое сравнение коллекций: `MachineConfiguration.Menu` сравнивается по правилам объекта коллекции, обычно по ссылке. Два конфигурационных снимка с одинаковым набором напитков не обязаны быть равны через `==`, потому что контейнеры разные.

**Разделение ответственности.** Напиток знает свои ограничения, заказ — цену добавок, способ оплаты — правила списания, автомат — порядок действий. Файловое хранение и администраторский доступ находятся вне `Models`. Это уменьшает число классов по сравнению с отдельными иерархиями для каждого рецепта, не складывая всю логику в форму.

## Честные ограничения текущей модели

- Модель не получает `AdminAccess` и сама не проверяет пароль или администраторский сеанс. `UpdateConfiguration()` защищает этап заказа и ID, но авторизация обеспечивается вызывающим слоем. Нельзя утверждать, что пароль проверяется при каждой операции внутри `CoffeeMachine`.
- Состояние является учебной симуляцией: нет банка, PIN, фискализации, учёта запасов воды/зёрен/молока, ограниченного количества монет и выручки. `SplitChange()` предполагает неограниченную доступность номиналов. Карта безлимитная по требованию проекта.
- Время приготовления сама модель не отсчитывает: любой вызывающий код может вызвать `FinishPreparing()` сразу после `Pay()`. Отсчёт и визуальные эффекты выполняются вне модели.
- `Cash`/`Card` доступны как изменяемые объекты. Прямые `machine.Card.Insert()` или `machine.Cash.Insert(...)` обходят этапы автомата и могут нарушить перечисленные инварианты. Нормальный интерфейс должен обращаться через методы `CoffeeMachine`.
- `Reset()` не очищает компоненты оплаты напрямую. Корректность опирается на порядок действий: наличные уже списаны/возвращены, карта уже вынута. При обходе координатора это предположение можно нарушить.
- Конструкторы записей, `with`, `Snapshot()` и `Duplicate()` не проверяют данные автоматически. Корректность обеспечивается явными вызовами `Validate()` на границах использования. Для `null`-конфигурации нет отдельной понятной проверки, возможен `NullReferenceException`.
- Проверки ID локальные и строковые; формат GUID не доказывает глобальную уникальность. Проверка меню не требует хотя бы одного включённого напитка.
- Изменения модели сами по себе не сохраняются в JSON: это обязанность слоя хранения. Конфигурация не содержит текущего заказа, сдачи или положения карты; копирование настроек не переносит состояние обслуживания.
- Методы не синхронизированы для многопоточного доступа. Самостоятельность экземпляров обеспечивается их собственными полями, а не потокобезопасностью.
- Для общей утилиты `SplitChange()` нет верхнего ограничения суммы; необычно большая сумма создаст длинный список. Для обычных сумм интерфейса это практическое ограничение не проявляется.
