# CoffeeAutomat: короткая шпаргалка для защиты

Полное объяснение и ссылки на все классы/методы — в [DEFENSE.md](DEFENSE.md).

## Выступление на 2–3 минуты

> Программа — симулятор кофейных автоматов на C# и Windows Forms. Покупатель выбирает кофе и добавки, оплачивает наличными или демонстрационной картой, получает напиток и сдачу. Администратор по паролю редактирует меню и управляет автоматами. Настройки сохраняются в JSON.
>
> Я разделил код на модель, интерфейс и хранение. Модель определяет правила: цену, допустимые действия и этапы заказа. Формы отображают эти данные и вызывают методы модели. Хранилище читает и записывает настройки. Поэтому правила покупки можно тестировать без открытия окна.
>
> Главный объект — CoffeeMachine. Он хранит текущий заказ, оплату и состояние. MachineConfiguration — отдельный объект сохранённых настроек. CoffeeMachineControl — визуальный компонент. Чтобы поставить второй автомат рядом, создаются новые экземпляры модели и компонента, а не копируется код формы.
>
> Разные виды кофе представлены данными Beverage, потому что отличаются рецептом и параметрами, а не устройством программы. Новый напиток добавляется через админку без пересборки. Заказ CoffeeOrder содержит добавки и вычисляет итоговую стоимость. Для денег используется decimal.
>
> Наличные и карта реализуют IPaymentMethod. Автомат вызывает единый метод Pay, а конкретный объект выполняет свой вариант оплаты. Это пример полиморфизма. Состояния Choosing, Paying, Brewing и Ready не позволяют готовить без оплаты и получать один заказ несколько раз.
>
> Изменения меню сначала проверяются и сохраняются во временный файл, который затем заменяет основной JSON. После успешной записи обновляется работающий автомат. Пароль хранится в виде PBKDF2-хеша со случайной солью. Это локальная защита учебного приложения, а не банковская система.
>
> В проекте есть 31 проверка модели, сохранения и доступа. Реальное оборудование, банковские платежи и история продаж не реализованы: они могут быть следующими этапами развития.

## Что выучить в первую очередь

| Если спрашивают | Короткий ответ |
|---|---|
| Где начинается программа? | `Program.Main()` настраивает приложение и запускает `MainForm` |
| Кто главный в логике покупки? | `CoffeeMachine`; форма обращается к нему при нажатии кнопок |
| Где считается стоимость? | В вычисляемом свойстве `CoffeeOrder.Total` |
| Где описан рецепт? | В записи `Beverage` |
| Где меню конкретного автомата? | `MachineConfiguration.Menu` |
| Где сохраняется? | `JsonMachineStore`, файл `%LOCALAPPDATA%\CoffeeMachineApp\machines.json` |
| Где проверяется пароль? | `AdminAccess`; ввод находится в `AdminLoginForm` |
| Где инкапсуляция? | Закрытые сеттеры состояния и проверяемые методы переходов |
| Где полиморфизм? | `IPaymentMethod.Pay()` у наличных и карты |
| Где наследование? | Собственные окна и контролы наследуют `Form`, `UserControl`, `Button`, `Control` |
| Где композиция? | Автомат содержит заказ и платёжные объекты; окно содержит несколько автоматов |
| Почему нет класса на каждый напиток? | Различия рецептов задаются данными, новые алгоритмы им пока не нужны |
| Зачем `with`? | Создать изменённую запись, сохранив прежний объект |
| Зачем `Snapshot`? | Снять собственную копию контейнера меню, сохранив ID |
| Зачем `Duplicate`? | Создать настройки другого автомата с новыми ID автомата и напитков |
| Зачем два вида `Program`? | Два проекта: один запускает окно, другой — консольные проверки |
| Почему не база данных? | Малый локальный каталог, один записывающий процесс, нет истории и сложных запросов |
| Почему не `Thread.Sleep`? | Он заблокировал бы окно; кадры обновляются UI-таймером |
| Почему не хватает скрытия кнопки админки? | Доступ дополнительно проверяется в обработчиках изменения и сохранения |

## Покупка в одной строке

`Select → Configure → BeginPayment → InsertMoney / InsertCard → Pay → FinishPreparing → CollectDrink / CollectChange / EjectCard → Reset`.

Это схема: перед картой выбирается `SelectPayment(true)`; сдачу и карту можно получить ещё во время приготовления; `Reset()` приватный и вызывается автоматически, когда заказ полностью выдан. При отмене до оплаты используется `Cancel()`.

## О чём говорить точно

- «Шесть классов предметной модели», а не «во всей программе только шесть классов». Ещё есть интерфейс оплаты и перечисление состояний.
- «Хеширование пароля», а не «расшифровка пароля».
- «UI-таймеры в одном потоке», а не «каждый автомат в отдельном потоке».
- «Модель проверяет этапы покупки; главное окно проверяет доступ», а не «пароль проверяется в каждом методе модели».
- «31 проверка логики и хранения», а не «интерфейс и все возможные ошибки полностью протестированы».
- «Слои по обязанностям», а не «полноценный MVVM».
- «Уменьшен риск повреждения JSON при записи», а не «данные невозможно потерять при любом сбое».
