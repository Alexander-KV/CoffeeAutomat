# Сохранение настроек и вход администратора: материал для защиты

[Оглавление руководства](DEFENSE.md) · [Короткая шпаргалка](QUICK_DEFENSE.md)

Исходники: [JsonMachineStore.cs](../CoffeeMachineApp2/Storage/JsonMachineStore.cs), [AdminAccess.cs](../CoffeeMachineApp2/Storage/AdminAccess.cs), [AdminLoginForm.cs](../CoffeeMachineApp2/Forms/AdminLoginForm.cs), [Program.cs](../CoffeeMachineApp2/Program.cs).

Раздел проверен по актуальным файлам `CoffeeMachineApp2/Storage/JsonMachineStore.cs`, `CoffeeMachineApp2/Storage/AdminAccess.cs` и `CoffeeMachineApp2/Forms/AdminLoginForm.cs`. Для объяснения подключения дополнительно проверены `Program.cs`, `MainForm.cs`, административные проверки в `CoffeeMachineControl.cs` и `MachineConfiguration.cs`. Ниже описано фактическое поведение проекта, а возможные доработки обозначены отдельно. Возможности отдельного класса не приравниваются к возможностям всего приложения.

## 1. Как объяснить эту часть проекта за минуту

«Я отделил хранение настроек от интерфейса. `IMachineStore` задаёт два действия: загрузить и сохранить конфигурации. `JsonMachineStore` реализует их через JSON: проверяет данные, записывает временный файл и только после успешной записи заменяет основной. `AdminAccess` отдельно отвечает за пароль и текущий сеанс администратора. Пароль не записывается открытым текстом: сохраняются случайная соль и результат PBKDF2-SHA256. `AdminLoginForm` собирает ввод, показывает ошибки и вызывает сервис доступа. При первом входе пользователь задаёт и подтверждает пароль, при следующих — вводит его. Права проверяются в обработчиках изменения автоматов, а не только скрытием кнопок. Это локальная защита учебного приложения; она не защищает от человека, который может изменить файлы или программу вне интерфейса».

## 2. Назначение типов и связь с ООП

| Тип | Назначение | Почему выделен отдельно |
| --- | --- | --- |
| `IMachineStore` | Контракт загрузки и сохранения списка `MachineConfiguration`. | `MainForm` может работать с хранилищем через интерфейс. Для другого формата или базы можно написать другую реализацию, сохранив контракт. Существующий интерфейс не означает, что база данных уже реализована. |
| `JsonMachineStore : IMachineStore` | Реализация хранения в JSON, проверка целостности данных, создание стандартного набора при отсутствии файла. | Файловые операции не смешаны с отрисовкой формы или приготовлением кофе. |
| `AdminAccess` | Создание пароля, проверка введённого пароля, хранение признака текущего входа и проверка административных прав. | Один объект доступа используется главным окном и автоматами, поэтому режим администратора общий. |
| `AdminLoginForm : Form` | Диалог первичного задания пароля или последующего входа. | Форма отвечает за поля, кнопки и сообщения; вычисление хеша и запись файла выполняет `AdminAccess`. |

Здесь есть **инкапсуляция**: путь хранится в закрытом поле, а менять `IsAdmin` извне нельзя. Есть **абстракция и полиморфизм**: `MainForm` получает `IMachineStore`, а фактически вызывает реализацию `JsonMachineStore`. Есть **наследование**: окно входа наследуется от WinForms `Form`. Хранилище и сервис доступа объявлены `sealed`, поэтому их нельзя наследовать; это не мешает подменять реализацию интерфейса хранилища. Новый класс на каждый напиток для этого не нужен.

## 3. `IMachineStore`: все объявленные методы

У интерфейса нет полей, свойств и конструктора. Объявлены ровно два метода:

| Метод | Поведение по контракту | Причина такого контракта |
| --- | --- | --- |
| `IReadOnlyList<MachineConfiguration> Load()` | Возвращает список конфигураций; конкретные правила чтения определяет реализация. | Вызывающей стороне нужен набор настроек, а не знание о JSON и путях. `IReadOnlyList` предоставляет чтение элементов и количества без методов изменения списка. Это не обещание абсолютной неизменяемости любого возможного объекта реализации. |
| `void Save(IReadOnlyList<MachineConfiguration> machines)` | Принимает полный актуальный список конфигураций для сохранения. | В одном файле хранится весь состав автоматов; создание, удаление и изменение меню используют одну операцию сохранения. |

## 4. `JsonMachineStore`: поля и свойство

| Член | Что хранит или возвращает | Зачем нужен |
| --- | --- | --- |
| `private readonly string _path` | Полный путь к JSON-файлу, зафиксированный конструктором. | Относительный путь преобразуется один раз; последующая смена рабочей папки не меняет выбранный файл. `readonly` запрещает переназначать поле после создания объекта. |
| `private static readonly JsonSerializerOptions Options` | Общие параметры сериализатора: `WriteIndented = true` и `JavaScriptEncoder.UnsafeRelaxedJsonEscaping`. | JSON форматируется с отступами; кириллица остаётся читаемой. Ослабленное экранирование используется для локального JSON-файла: такой текст нельзя без дополнительной обработки вставлять в HTML или JavaScript. `readonly` фиксирует ссылку на объект параметров, а не делает любой объект автоматически неизменяемым. |
| `public static string DefaultPath` | `%LOCALAPPDATA%\CoffeeMachineApp\machines.json` на Windows. Фактически путь собирается через `Environment.GetFolderPath(LocalApplicationData)` и `Path.Combine`. | Настройки принадлежат текущему пользователю ОС и находятся отдельно от `.exe`, чтобы обычное обновление программы не заменяло их. Свойство вычисляет путь, но само не создаёт файл. |

### Все объявленные методы и конструктор

| Член | Что именно делает | Почему сделано так |
| --- | --- | --- |
| `public JsonMachineStore(string path)` | Вызывает `Path.GetFullPath(path)` и сохраняет результат в `_path`. Не читает файл и не создаёт каталог. | Позволяет использовать стандартный путь в приложении и отдельный временный путь в проверках. |
| `public IReadOnlyList<MachineConfiguration> Load()` | Если файла нет, создаёт массив с одним `MachineConfiguration.CreateDefault()`, сохраняет через `Save()` и возвращает его. Если файл есть, читает текст, десериализует `List<MachineConfiguration>`, вызывает `Validate()`, затем возвращает массив снимков через `Snapshot()`. | Первый запуск сразу получает рабочее меню. Существующие ошибочные данные не подменяются стандартными молча. Снимки отделяют возвращённые коллекции меню от исходных списков, созданных десериализатором. |
| `public void Save(IReadOnlyList<MachineConfiguration> machines)` | Сначала вызывает `Validate()`. Создаёт каталог, записывает JSON в уникальный временный файл рядом с целевым, вызывает `Flush(true)`, закрывает поток и делает `File.Move(temporary, _path, true)`. В `finally` удаляет оставшийся временный файл. | Основной файл не обрезается перед записью; заменяется только полностью записанным кандидатом. Ошибки перед заменой не должны уничтожать предыдущий корректный файл. |
| `private static void Validate(IReadOnlyList<MachineConfiguration> machines)` | Отклоняет `null`, пустой список, более 12 автоматов и `null` среди элементов. Вызывает `Validate()` каждой конфигурации. Проверяет уникальность ID автоматов через `Distinct()`. | Нельзя сохранить или загрузить структуру, нарушающую ограничения модели. Проверка нужна и при чтении: JSON можно изменить вне интерфейса. |

`MachineConfiguration.Validate()` дополнительно проверяет формат ID, непустое название длиной не более 40 символов, меню из 1–100 непустых рецептов, каждый рецепт и уникальность ID напитков внутри меню. Это проверка данных; она не проверяет пароль.

### Как работает атомарное сохранение

Последовательность в `Save()`:

1. Проверить весь список до файловой записи.
2. Убедиться, что каталог существует.
3. Создать соседний файл вида `machines.json.<случайный GUID>.tmp` с `FileMode.CreateNew`, `FileAccess.Write` и `FileShare.None`.
4. Сериализовать конфигурации в поток. `CreateNew` не позволяет незаметно перезаписать уже существующий временный файл.
5. Вызвать `Flush(true)`, затем освободить поток через `using`.
6. Переместить готовый файл на место основного с разрешением замены: `File.Move(..., true)`.
7. В `finally` попытаться убрать временный файл, если он ещё существует.

На обычной локальной файловой системе замена соседнего файла позволяет наблюдать старую или новую полную версию вместо наполовину записанного JSON. Это смысл атомарности в данном проекте. **Факт:** `JsonMachineStore` выполняет сброс записанного файла и замену; **граница:** сам этот класс не реализует транзакцию базы данных, резервную копию или межпроцессную блокировку. **В приложении межпроцессная защита есть:** её обеспечивает `Program.Main()` перед созданием главного окна. Атомарная замена и блокировка второго экземпляра решают разные задачи. Ни одна из них не даёт абсолютной гарантии сохранности при любом сбое накопителя/ОС. При жёстком завершении процесса `finally` может не выполниться и временный файл может остаться.

### Почему второй экземпляр не перезаписывает настройки первого

В штатной точке входа `Program.Main()` перед `Application.Run(...)` выполняется:

```csharp
using var appLock = new FileStream(
    path + ".lock", FileMode.OpenOrCreate, FileAccess.ReadWrite, FileShare.None);
Application.Run(new MainForm(new JsonMachineStore(path)));
```

При стандартном пути используется соседний файл `%LOCALAPPDATA%\CoffeeMachineApp\machines.json.lock`. `FileShare.None` запрещает другому экземпляру открыть этот же файл, пока первый держит поток. Область действия `using var` охватывает весь `Application.Run()`: блокировка удерживается в течение работы главного окна и освобождается при выходе из области. Второй штатный запуск с тем же путём получает файловую ошибку до открытия главного окна; `Program.Main()` показывает сообщение, в том числе с предложением закрыть другой экземпляр.

Значимо открытое владение файлом, а не одно наличие `.lock` на диске. Оставшийся после завершения файл сам по себе не запрещает новый запуск: используется `OpenOrCreate`. Блокировка действует для экземпляров, использующих ту же точку входа и тот же путь. Она не превращает `JsonMachineStore` в самостоятельное многопроцессное хранилище и не мешает внешнему редактору напрямую изменить `machines.json`, игнорируя отдельный `.lock`.

Если файл отсутствует, стандартные настройки создаются автоматически. Если файл существует, но JSON повреждён, десериализация или валидация выдаёт исключение; основной файл не перезаписывается стандартным меню. Ошибки файловой системы также передаются вызывающему коду. В самом хранилище нет `MessageBox`: показ сообщения — ответственность интерфейса.

В `machines.json` сохраняются **конфигурации** автоматов и рецепты. Текущий заказ, приготовление, вставленная карта, деньги покупателя и административный сеанс сюда не записываются.

## 5. `AdminAccess`: поля и свойства

| Член | Фактическое значение или поведение | Назначение |
| --- | --- | --- |
| `private const int Iterations = 210000` | Число итераций PBKDF2 для нового пароля. | Делает каждую проверку дороже, чем один быстрый хеш, и замедляет перебор. Это не счётчик неудачных входов. |
| `private readonly string _path` | Полный путь к файлу доступа. | Отделяет файл учётных данных от конфигураций автоматов. |
| `public bool IsAdmin { get; private set; }` | Признак входа в текущем объекте. Изначально `false`. | Остальной код может читать состояние, но не может присвоить ему `true` напрямую через свойство. В файл этот признак не сохраняется. |
| `public bool HasPassword => File.Exists(_path)` | Проверяет наличие файла. Не проверяет его содержимое. | От этого зависит предложение первичной настройки. Повреждённый существующий файл считается существующим паролем и не вызывает автоматический сброс. |

### Все объявленные методы и конструктор

| Член | Что именно делает | Почему сделано так |
| --- | --- | --- |
| `public AdminAccess(string path)` | Преобразует путь через `Path.GetFullPath()` и сохраняет его. Не читает пароль и не авторизует пользователя. | При каждом новом запуске создаётся новый объект с `IsAdmin == false`; наличие файла само по себе не даёт права. |
| `public void CreatePassword(string password)` | Отклоняет существующий файл. Проверяет длину 6–128 символов и запрещает строку только из пробельных символов. Создаёт случайную соль 16 байт, вычисляет PBKDF2-SHA256 длиной 32 байта с 210 000 итераций. Записывает версию, параметры, соль и хеш в новый временный JSON, сбрасывает поток, затем перемещает файл без разрешения перезаписи. Только после успешного перемещения присваивает `IsAdmin = true`. В `finally` очищает буфер вычисленного хеша и убирает оставшийся временный файл. | Первый вход одновременно создаёт пароль и открывает сеанс. Ошибка создания файла не должна выдавать новый доступ. Запрет перезаписи защищает уже существующий пароль, включая ситуацию, когда другой процесс успел создать файл после начальной проверки. Подтверждение пароля проверяется формой, а не этим методом. |
| `public bool Login(string password)` | Сначала сбрасывает `IsAdmin` в `false`. Если файла нет — исключение. Для `null` или строки длиннее 128 возвращает `false`. Проверяет размер файла до чтения, разбирает JSON, версию и параметры. Вычисляет PBKDF2 для введённого пароля с сохранённой солью и числом итераций. Сравнивает результат с сохранённым через `FixedTimeEquals`, записывает результат в `IsAdmin` и возвращает его. Вычисленный буфер `actual` очищает в `finally`. | Неправильный пароль или ошибка повторного входа не сохраняет прежний статус администратора. Сравнение не завершается досрочно на первом отличающемся байте. Повреждённые файлы не принимаются за успешный вход. |
| `public void Logout()` | Присваивает `IsAdmin = false`. Файл не удаляет. | Завершает текущий сеанс, сохраняя пароль для следующего входа. |
| `public void RequireAdministrator()` | Если `IsAdmin == false`, выбрасывает `UnauthorizedAccessException` с понятным сообщением. При наличии доступа просто возвращает управление. | Даёт общую проверку прав перед изменением конфигурации; защита не ограничивается видимостью кнопок. Метод сам ничего не сохраняет и не открывает окно входа. |

### Формат файла и точные проверки

В файл доступа записывается объект с четырьмя полями:

| Поле JSON | Содержание |
| --- | --- |
| `Version` | Сейчас `1`; неподдерживаемая версия не принимается. |
| `Iterations` | При создании `210000`; при входе допустимо от `100000` до `1000000`. Сохранённое значение позволяет проверить пароль с теми параметрами, с которыми он был создан; автоматического обновления параметров нет. |
| `Salt` | Случайные 16 байт, представленные строкой Base64. |
| `Hash` | Результат PBKDF2 длиной 32 байта, представленный строкой Base64. |

Перед разбором отклоняется файл длиннее 4096 байт. Проверяются наличие и тип обязательных полей, версия, допустимое число итераций, корректность Base64 и длины массивов. Некоторые ошибки формата оборачиваются в `InvalidDataException` с сообщением о повреждении; явные проверки тоже выбрасывают `InvalidDataException`. Ошибки чтения не маскируются под неверный пароль. Файл при неудачном входе не меняется.

**Соль** не является секретом: она хранится рядом с хешем. Она делает результат различным для одинаковых паролей и затрудняет применение заранее подготовленных таблиц перебора. **PBKDF2** многократно использует псевдослучайную функцию на основе HMAC-SHA256 для получения проверочного значения. Проверка входа повторяет вычисление; извлекать исходный пароль из файла для этого не требуется.

Правильные слова на защите: «пароль хешируется с солью через PBKDF2-SHA256» или «используется функция выработки ключа PBKDF2». **Это не шифрование пароля:** здесь нет ключа расшифровки и операции восстановления исходной строки. Base64 тоже не шифрование, а текстовое представление байтов. Хеш не отменяет возможность подбора слабого пароля.

`CryptographicOperations.ZeroMemory()` уменьшает время нахождения вычисленного результата в явно доступном массиве памяти. Не следует утверждать, что код гарантированно стирает все копии пароля из памяти: исходный пароль приходит как управляемая строка, а `TextBox.Clear()` лишь очищает поле ввода. В `CreatePassword()` блок `finally` начинается после создания каталога, поэтому ранняя ошибка до этого блока не попадает в его очистку.

### Пути и связь с главным окном

При обычном запуске Windows используются:

```text
%LOCALAPPDATA%\CoffeeMachineApp\machines.json
%LOCALAPPDATA%\CoffeeMachineApp\admin-access.json
```

`MainForm` создаёт `AdminAccess` через `Path.Combine(Path.GetDirectoryName(JsonMachineStore.DefaultPath), "admin-access.json")`. Поэтому в штатной конфигурации файлы находятся рядом. Оба сервиса принимают произвольный путь для проверок, но **факт реализации:** если вручную передать в `MainForm` хранилище с другим путём, путь авторизации автоматически за ним не последует — главное окно по-прежнему использует каталог `DefaultPath`. **Возможная доработка:** передавать сервис доступа или общие пути через конструктор главной формы.

Один экземпляр `AdminAccess` разделяется между главным окном и компонентами автоматов. При запуске программа остаётся в режиме покупателя. Главное окно разрешает открыть диалог входа, только когда нет текущих заказов; модель сохраняет заказ до получения необходимых кофе, карты и сдачи. Это условие контролируется главным окном и моделью, а не самим `AdminAccess`.

После успешного входа главное окно обновляет видимость административных элементов, а компоненты автоматов блокируют покупательские действия. Перед добавлением, копированием через добавление, удалением и сохранением конфигураций обработчики вызывают `RequireAdministrator()`. При выходе меняется общий признак доступа и обновляются компоненты.

**Граница ответственности:** `JsonMachineStore.Save()` не проверяет пароль. Первоначальное создание стандартного файла при `Load()` также возможно в режиме покупателя. Проверка административных изменений встроена в обычный сценарий приложения, но код, который напрямую вызовет хранилище, не получит автоматическую проверку доступа от самого хранилища.

| --- | --- | --- |

## 8. Двенадцать вопросов преподавателя с короткими ответами

1. **Зачем `IMachineStore`, если реализация пока одна?** Он отделяет главное окно от способа хранения и позволяет подставить другое хранилище без изменения контракта `Load`/`Save`. В проекте сейчас используется JSON.

2. **Почему JSON, а не база данных?** Хранится небольшой список до 12 автоматов и их меню; нужен простой переносимый локальный файл без сервера. Транзакции нескольких пользователей и история изменений здесь не реализованы; при таких требованиях решение надо расширять.

3. **Где лежат файлы и почему не рядом с `.exe`?** В штатном запуске — `%LOCALAPPDATA%\CoffeeMachineApp`: `machines.json` и `admin-access.json`. Это пользовательские данные, которые не нужно записывать в каталог установленной программы и заменять при её обновлении.

4. **Что означает атомарное сохранение и можно ли запустить два экземпляра?** Сначала полностью записывается соседний временный файл и выполняется `Flush(true)`, потом он заменяет основной. Это защищает от неполной записи, но не является резервной копией. От второго штатного экземпляра с тем же файлом данных отдельно защищает `Program.Main()`: он держит `.lock` открытым с `FileShare.None` весь срок работы окна.

5. **Что произойдёт при повреждённом `machines.json`?** Чтение или проверка данных выдаст исключение; файл не будет молча заменён стандартным меню. Стандартное меню создаётся только при отсутствии файла.

6. **Зачем проверять данные и при чтении, и при записи?** При записи проверяется состояние, переданное кодом, а при чтении — внешние данные, которые могли отредактировать вручную. Проверяются размеры списков, обязательные значения и уникальность ID, затем ограничения каждой модели.

7. **Пароль зашифрован?** Нет. Сохраняется результат PBKDF2-SHA256 с солью: 210 000 итераций, соль 16 байт, результат 32 байта. При входе результат вычисляется заново и сравнивается; расшифровки нет.

8. **Почему соль хранится открыто и что она даёт?** Соль не обязана быть секретной. Случайная соль делает хеши одинаковых паролей различными и препятствует эффективному повторному использованию заранее рассчитанных таблиц. Слабый пароль всё равно можно подобрать.

9. **Почему используется `FixedTimeEquals`?** Сравнение не прекращается на первом различающемся байте и уменьшает утечку информации через время самого сравнения. Это не означает, что весь вход выполняется за абсолютно одинаковое время.

10. **Как первый вход отличается от последующего?** При отсутствии файла форма просит пароль и подтверждение; сервис проверяет требования и создаёт файл без перезаписи существующего. Затем нужен сохранённый пароль. После перезапуска статус администратора не сохраняется.

11. **Где реально проверяются права?** В `MainForm` перед добавлением, удалением и сохранением вызывается `RequireAdministrator()`; копирование проходит через защищённое добавление. Компоненты ещё скрывают настройки и блокируют покупки в режиме администратора. `JsonMachineStore` проверяет данные, но не пароль.

12. **Можно ли обойти вход, имея доступ к папке приложения?** Имея право записи в папку данных, можно удалить или заменить файл доступа; удаление вернёт первичную настройку. Это известная граница локальной учебной защиты. Защита от такого пользователя требует других механизмов, которых в текущем проекте нет.

## 9. Что удобно показать преподавателю

1. Открыть `IMachineStore`, затем его реализацию и точку передачи интерфейса в `MainForm`.
2. Показать `Validate()` перед записью и после чтения.
3. В `Save()` последовательно указать временный путь, `CreateNew`, `Flush(true)`, `File.Move(..., true)` и `finally`. Затем в `Program.Main()` показать отдельную блокировку `.lock` и объяснить срок её удержания через `using var` вокруг `Application.Run()`.
4. В `AdminAccess.CreatePassword()` показать соль, PBKDF2, поля JSON и отличие `File.Move(..., false)`: пароль нельзя заменить повторным созданием через этот метод.
5. В `Login()` показать сброс сеанса до проверки и `FixedTimeEquals`; затем `RequireAdministrator()` и его вызов перед сохранением.
6. В окне входа продемонстрировать неверное подтверждение или пароль. Использовать отдельную папку тестовых данных, если нужно демонстрировать первый вход, чтобы не удалять рабочий файл доступа.

Свойства описаны отдельно; автоматически генерируемые компилятором аксессоры и унаследованные методы `Form` не выдаются за авторские методы проекта.
